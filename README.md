# licguard

A fast, single-binary CLI that inventories your project's open source dependencies, normalizes their licenses to SPDX, and checks them against your license policy — locally and as a CI gate.

> **Status: pre-alpha.** Nothing is usable yet. See the [PRD](docs/prd.md) for the plan.

- npm first (`package-lock.json`, yarn, pnpm), Java (Maven, Gradle via CycloneDX SBOM) next.
- Policy in a versioned `licguard.toml`: allow, review and deny lists, dated waivers, and license clarifications for packages with wrong metadata.
- Deterministic exit codes, JSON output, and GitHub annotations.
- No telemetry; nothing leaves your machine except queries to the package registries.

## Installation

- **Homebrew** (macOS, Linux):

  ```sh
  brew install baotista/tap/licguard
  ```

- **Installer scripts**, which download the binary from the latest GitHub Release:

  ```sh
  # macOS, Linux
  curl --proto '=https' --tlsv1.2 -LsSf https://github.com/baotista/licguard/releases/latest/download/licguard-installer.sh | sh
  ```

  ```powershell
  # Windows
  powershell -ExecutionPolicy Bypass -c "irm https://github.com/baotista/licguard/releases/latest/download/licguard-installer.ps1 | iex"
  ```

- **Cargo**, which builds it from crates.io:

  ```sh
  cargo install licguard
  ```

- **Docker**, with the Project mounted at `/work`:

  ```sh
  docker run --rm -v "$PWD:/work" ghcr.io/baotista/licguard check
  ```

- **GitHub Releases**: download the archive for your platform from the [releases page](https://github.com/baotista/licguard/releases) and check it against the `.sha256` next to it. Binaries are built for Linux (x86_64 and aarch64, static musl), macOS (x86_64 and Apple silicon) and Windows (x86_64).

### Private npm registries

Packages whose license is in neither the lockfile nor `node_modules` get it from the npm registry. licguard finds that registry the way npm does, so a Project that installs from a private registry or a mirror needs no extra setup:

1. `LICGUARD_NPM_REGISTRY`, which names the registry of every Package and overrides everything below;
2. the `npm_config_registry` environment variable;
3. the Project's `.npmrc`, then the user's (`NPM_CONFIG_USERCONFIG`, else `~/.npmrc`): `registry=`, and `@scope:registry=` for the Packages of a scope;
4. else `https://registry.npmjs.org`.

Global and builtin npm configuration files are not read. A credential, `//host/path/:_authToken=` or `//host/path/:_auth=`, is sent only to the URLs under the registry it names, never to another host, not even on a redirect, and never appears in the output or the license cache. `${VAR}` references are expanded from the environment, e.g. `//npm.example.com/:_authToken=${NPM_TOKEN}`. `username` and `_password` are not supported: use a token. Proxies come from `ALL_PROXY`, `HTTPS_PROXY` or `HTTP_PROXY`, and `NO_PROXY`.

## GitHub Action

The action installs the released licguard binary, restores its license cache, and runs `licguard check --format github`: each Violation is annotated on its lockfile entry in the pull request, and a summary is added to the job. It runs on Linux, macOS and Windows runners.

Start in **observation mode**: the step reports the Violations but never fails, while you fix them or cover them with Waivers (`licguard waive`).

```yaml
# .github/workflows/licenses.yml
name: Licenses

on:
  pull_request:
  push:
    branches: [main]

jobs:
  licguard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: baotista/licguard@v0
        with:
          observe: true
```

Then switch to **gate mode** by removing `observe`: the step fails on any Violation, which blocks the pull request once the job is a required status check.

```yaml
      - uses: baotista/licguard@v0
        with:
          args: --strict  # optional: `review` Verdicts fail too
```

| Input | Default | Description |
| --- | --- | --- |
| `version` | `latest` | The licguard release to install, e.g. `v0.1.0`. Pin it for reproducible runs. |
| `path` | `.` | The Project directory, the one holding `licguard.toml` |
| `args` | | Extra arguments to `licguard check`, split on whitespace, e.g. `--strict --include-dev` |
| `observe` | `false` | `true` for observation mode: annotate and summarize, never fail |
| `token` | `${{ github.token }}` | The token used to resolve `latest` through the GitHub API |

The license cache lives in `${{ runner.temp }}/licguard-cache` (exported as `LICGUARD_CACHE_DIR`) and is saved with `actions/cache`, keyed by the runner OS and the Project's lockfiles.

## Not legal advice

licguard applies the policy **you** define. The template generated by `licguard init` is a starting point, not a recommendation; have your policy validated by your own legal counsel.

## Releasing

Releases are built by [`dist`](https://github.com/axodotdev/cargo-dist) (config in `dist-workspace.toml`).

1. Bump `version` in `Cargo.toml` and merge it to `main`.
2. In the Actions tab, open the `Release` workflow, choose **Run workflow** on `main`, and enter the tag `vX.Y.Z`, which must match the version in `Cargo.toml`. You don't push the tag: the workflow creates it on that commit along with the GitHub Release. Leave the default `dry-run` to build every platform without publishing anything.
3. The workflow builds the binaries for every platform and publishes a GitHub Release with archives, SHA-256 checksums and the shell and PowerShell installers. Then, for a non-prerelease version, it publishes:
   - the Homebrew formula to [`baotista/homebrew-tap`](https://github.com/baotista/homebrew-tap);
   - the crate to crates.io (`.github/workflows/publish-crates.yml`);
   - the container image `ghcr.io/baotista/licguard`, tagged with the version and `latest`, for `linux/amd64` and `linux/arm64` (`.github/workflows/publish-container.yml`).
4. Move the action's major tag to the new release, so that `baotista/licguard@v0` uses it: `git tag -f v0 vX.Y.Z && git push -f origin v0`.

### One-time setup

Before the first release:

1. Create the public repository `baotista/homebrew-tap`, with a README and nothing else.
2. Add these repository secrets to `baotista/licguard` (Settings > Secrets and variables > Actions):
   - `HOMEBREW_TAP_TOKEN`: a fine-grained personal access token with the `Contents: Read and write` permission on `baotista/homebrew-tap` only;
   - `CARGO_REGISTRY_TOKEN`: a crates.io API token with the `publish-new` and `publish-update` scopes (restrict it to the `licguard` crate after the first publish).

After the first release:

1. Check that the crate name is reserved: the first `cargo publish` of the release claims `licguard` on crates.io. If it failed, run `cargo publish` from the release tag.
2. Make the container package public: on the `licguard` package page of `baotista`, Package settings > Change visibility > Public (GitHub creates it private).
3. Publish the action on the GitHub Marketplace: edit the release page, tick "Publish this Action to the GitHub Marketplace", accept the agreement and pick the categories.
4. Create the `v0` tag on the release (step 4 above, without `-f` the first time).
